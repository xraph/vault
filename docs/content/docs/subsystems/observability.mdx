title: Observability
description: The spans and metrics Vault records, and how you turn them on.
---

In a Forge app you don't have to do anything. Register the extension and Vault's spans go to the tracer provider `forge.New` installs, while its metrics land on `/_/metrics` next to forge's own. Outside Forge you pass a metrics sink yourself, and the spans go to whatever global OpenTelemetry tracer provider your process sets.

## Turning it on

With the Forge extension, the app's metrics are wired in for you. The extension passes `app.Metrics()` to the vault before any `WithVaultOption` options you give it (so a `vault.WithMetrics` of your own still wins), and it hands the same sink to the confy source when `mount_to_confy` is on.

Using Vault as a library, pass a `github.com/xraph/go-utils/metrics` sink to `vault.New`:

```go
v, err := vault.New(
    vault.WithStore(st),
    vault.WithEncryptionKey(key),
    vault.WithMetrics(app.Metrics()), // any go-utils metrics.Metrics
)
```

That one option reaches the secret service, the flag engine and the rotation manager. If you build those yourself, each takes the same sink through its own option:

| Option | Records |
|--------|---------|
| `vault.WithMetrics(m)` | Everything below that `vault.New` builds |
| `secret.WithMetrics(m)` | Secret operations, encrypt and decrypt calls |
| `flag.WithMetrics(m)` | Flag evaluations (an `EngineOption`) |
| `rotation.WithMetrics(m)` | Rotation attempts and their duration |
| `confy.WithSourceMetrics(m)` | Polls of the confy config source |
| `source.WithMetrics(m)` | Polls of `source.Database` |

A nil sink, the default, records nothing. Spans need no option at all.

Vault doesn't time its own database queries. Grove does that for every driver: a `db.client` span per query and the `db_client_operation_duration_seconds` histogram. A Grove span only starts under an existing parent, so Vault's spans also give the queries behind a secret read, a rotation or a config change something to nest under. Without them, a background rotation's queries would show up in the histogram and nowhere in a trace.

## Spans

Every span is kind `Internal` and carries the instrumentation scope `github.com/xraph/vault`.

| Span | Started by | Attributes |
|------|------------|------------|
| `get secret` | `secret.Service.Get` | `vault.secret.found` (bool), `vault.secret.encrypted` (bool, when found) |
| `get secret version` | `secret.Service.GetVersion` | `vault.secret.found`, `vault.secret.encrypted` |
| `set secret` | `secret.Service.Set` | `vault.secret.encrypted` |
| `delete secret` | `secret.Service.Delete` | `vault.secret.found` |
| `backfill version encryption` | `secret.Service.BackfillVersionEncryption`, which the extension runs at start | `vault.backfill.scanned`, `vault.backfill.marked` (ints) |
| `evaluate flag` | `flag.Engine.Evaluate` on a cache miss, and every `EvaluateDetail` | `vault.flag.explain` (bool), `vault.flag.found` (bool), `vault.flag.reason` (`disabled`, `tenantOverride`, `rule`, `default`) |
| `rotate secret` | `rotation.Manager.RotateNow` and the scheduled loop | `vault.rotation.trigger` (`scheduled`, `manual`) |
| `rotate due secrets` | A scheduled pass with at least one due policy this replica can rotate | `vault.rotation.due`, `vault.rotation.claimed`, `vault.rotation.failed` (ints) |
| `notify config watchers` | A confy source or `source.Database` poll that found a change | `vault.config.source` (`confy`, `database`), `vault.config.changed` (int) |

The secret, flag and rotation spans are children of whatever span your context carries, so in a Forge app they sit under the request. A cache hit on a flag gets no span: it's the hot path and nothing runs under it.

The rotation loop and the two pollers outlive the call that started them: `rotation.Manager.Start` (which forge runs inside its `start vault` span), or the first `Watch`. Each loop keeps that context's values and cancellation but drops its span. That matters because Grove starts a `db.client` span under any valid parent, even one that ended long ago, so without it every idle tick's policy list or config read would pile into the boot or request trace forever. Now those idle reads belong to no trace at all, and you still see their timing in `db_client_operation_duration_seconds`.

When a tick does find work, it starts `rotate due secrets` or `notify config watchers` as the root of a new trace, and the work happens under it: the claims and each `rotate secret` in a scheduled pass, or every `WatchFunc` that `source.Database` calls, which gets the notify span's context. A pass or a poll that finds nothing starts no span. `source.Database.Watch` still reads the key once on your context, since that read is part of your call.

Vault doesn't treat a missing secret or flag as a failure. The span says `found=false` and keeps an unset status. A real failure sets the status to `Error` with a short description, and adds one `exception` event whose only attribute is `exception.type`:

| Description | When |
|-------------|------|
| `decrypt failed` | A secret row the configured key can't open |
| `no rotator registered` | `RotateNow` for a key with no rotator |
| `read current secret failed` | Rotation couldn't read the secret it was rotating |
| `rotator failed` | Your rotator returned an error |
| `store new value failed` | Rotation couldn't write the new value |
| `claim failed` | The scheduled pass couldn't claim a due policy |
| The error type | Anything else: a Vault sentinel name such as `ErrDecryptionFailed`, or the Go type of the innermost error |

`exception.type` is always the sentinel name or the Go type.

## Metrics

Forge scrapes every metric with its namespace prefix, so `vault_flags_evaluated_total` appears as `forge_vault_flags_evaluated_total`. Outside Forge the name is whatever your sink makes of the bare one.

| Scraped name | Type | Labels |
|--------------|------|--------|
| `forge_vault_secret_operations_attempted_total` | Counter | `op` (`get`, `get_version`, `set`, `delete`), `result` (`ok`, `not_found`, `error`) |
| `forge_vault_crypto_operations_attempted_total` | Counter | `op` (`encrypt`, `decrypt`), `result` (`ok`, `error`) |
| `forge_vault_flags_evaluated_total` | Counter | `source` (`cache`, `store`), `result` (`ok`, `not_found`, `error`) |
| `forge_vault_rotations_attempted_total` | Counter | `trigger` (`scheduled`, `manual`), `result` (`ok`, `error`) |
| `forge_vault_rotation_duration_seconds` | Histogram | `trigger` (`scheduled`, `manual`), `result` (`ok`, `error`) |
| `forge_vault_config_sources_polled_total` | Counter | `source` (`confy`, `database`), `result` (`changed`, `unchanged`, `error`) |

The crypto counter covers the encrypt and decrypt calls the secret service makes on reads and writes. The backfill's trial decrypts stay out of it, since a row the key can't open is how the backfill tells plaintext from ciphertext.

The rotation histogram measures the whole attempt, your rotator included, with buckets at 5ms, 10ms, 50ms, 100ms, 500ms, 1s, 5s, 10s, 30s, 60s and 300s. The top one matches the five-minute claim lease a scheduled rotation has to finish inside.

A config source poll counts once. For `source.Database`, which reads each watched key on its own, `error` means at least one read failed on that tick.

A few queries to start from:

```text
# Share of flag evaluations the cache answered
sum(rate(forge_vault_flags_evaluated_total{source="cache"}[5m]))
  / sum(rate(forge_vault_flags_evaluated_total[5m]))

# Rows the configured key can't decrypt (a key mismatch or tampered data)
sum(rate(forge_vault_crypto_operations_attempted_total{op="decrypt", result="error"}[5m]))

# p95 rotation time, by trigger
histogram_quantile(0.95,
  sum by (le, trigger) (rate(forge_vault_rotation_duration_seconds_bucket[1h])))

# Config polls that failed
sum by (source) (increase(forge_vault_config_sources_polled_total{result="error"}[15m]))
```

## What never leaves Vault

None of these go on a span, an event, a status or a metric label: secret values, plaintext or ciphertext, key material, secret names, flag keys, config keys and values, app, tenant and user IDs, IP addresses, and error text. Secret names are on the list because they leak the shape of what you store. Error text is on it because store errors quote the key, and a rotator's error can quote the value it was rotating.

Logs are a different matter. The rotation manager and the audit logger write secret keys into their log lines. The Forge extension doesn't pass `e.Logger()` to the vault, so in a Forge app those lines go nowhere, but if you pass `vault.WithLogger` yourself, treat that log stream as sensitive.

## The metrics package

`github.com/xraph/vault/metrics` is deprecated. It defines a `Collector` of thirteen counters and histograms, but nothing in Vault ever recorded through it, so they always read zero. It stays so existing imports keep building. Use `vault.WithMetrics`.
