Vault ships a Forge extension in `extension/`. Register it with your app and it finds a store, builds the `*vault.Vault`, starts the rotation loop, optionally mounts Vault into Forge's config manager, and registers a dashboard contract contributor. It doesn't run migrations and doesn't mount any HTTP routes; both are covered below.

## Registering the extension

```go
package main

import (
    "log"

    "github.com/xraph/forge"
    grove "github.com/xraph/grove/extension"
    vaultext "github.com/xraph/vault/extension"
)

func main() {
    app := forge.NewApp(forge.AppConfig{
        Name: "billing-api",
        Extensions: []forge.Extension{
            grove.New(), // extensions.grove: driver and dsn
            vaultext.New(
                vaultext.WithAppID("billing"),
                vaultext.WithEncryptionKeyEnv("VAULT_ENCRYPTION_KEY"),
            ),
        },
    })

    if err := app.Run(); err != nil {
        log.Fatal(err)
    }
}
```

List Grove first, because Vault looks up the database during `Register`.

During `Register` the extension:

1. Loads its config from `extensions.vault` (or a top-level `vault` key) and merges your options in.
2. Picks a store: `WithStore`, then the database named by `WithGroveDatabase` or `grove_database`, then any `*grove.DB` already in the container. The Grove driver picks the PostgreSQL, SQLite or MongoDB store. With none of them, `Register` fails with `ErrNoStore`; there is no in-memory fallback.
3. Builds the `*vault.Vault` and logs a warning if no encryption key is configured.
4. Provides `*vault.Vault` and `store.Store` to the DI container.
5. Mounts Vault into Forge's config manager when `mount_to_confy` is on.

`Start` starts the rotation manager's background loop and a background backfill that marks which secret versions are encrypted. `Stop` cancels both, then closes the store. `Health` pings the store.

Resolve the Vault anywhere in your app:

```go
v, err := forge.Inject[*vault.Vault](app.Container())
if err != nil {
    log.Fatal(err)
}
```

## Migrations

The extension never calls `Migrate`, so `disable_migrate` and `WithDisableMigrate()` have no effect. On a fresh PostgreSQL or SQLite database the tables Vault reads and writes don't exist until something migrates them. Build the store yourself, call `Migrate`, and pass it in:

```go
drv := pgdriver.New()
if err := drv.Open(ctx, os.Getenv("DATABASE_URL")); err != nil {
    log.Fatal(err)
}
db, err := grove.Open(drv) // github.com/xraph/grove
if err != nil {
    log.Fatal(err)
}

store := postgres.New(db)
if err := store.Migrate(ctx); err != nil {
    log.Fatal(err)
}

ext := vaultext.New(
    vaultext.WithStore(store),
    vaultext.WithAppID("billing"),
)
```

## No HTTP routes

The extension mounts no REST API, so `base_path`, `disable_routes`, `WithBasePath` and `WithDisableRoutes` do nothing. The Forge dashboard reads Vault through the contract contributor instead (see [Dashboard](#dashboard)). If you need HTTP endpoints, write handlers that call the `*vault.Vault` you resolved from the container.

## Configuration

```yaml
extensions:
  vault:
    app_id: billing
    encryption_key_env: VAULT_ENCRYPTION_KEY   # hex or base64, 32 bytes once decoded
    flag_cache_ttl: 30s
    source_poll_interval: 30s
    grove_database: primary                    # optional; default *grove.DB otherwise
    mount_to_confy: true
    confy_key_prefix: "vault."
    confy_mount_patterns: ["db.*", "auth.*"]
```

| Key | Option | Default |
| --- | --- | --- |
| `app_id` | `WithAppID(id)` | empty |
| `encryption_key_env` | `WithEncryptionKeyEnv(name)` | empty, so secrets are stored unencrypted |
| `flag_cache_ttl` | `WithConfig(extension.Config{FlagCacheTTL: ...})` | `30s` |
| `source_poll_interval` | `WithConfig(extension.Config{SourcePollInterval: ...})` | `30s` |
| `grove_database` | `WithGroveDatabase(name)` | the default `*grove.DB` |
| `mount_to_confy` | `WithMountToConfy()` | `false` |
| `confy_key_prefix` | `WithConfyKeyPrefix(prefix)` | empty |
| `confy_mount_keys` | `WithConfyMountKeys(keys...)` | all keys |
| `confy_mount_patterns` | `WithConfyMountPatterns(globs...)` | all keys |
| `disable_migrate`, `disable_routes`, `base_path` | `WithDisableMigrate()`, `WithDisableRoutes()`, `WithBasePath(path)` | accepted, but do nothing (see above) |
| `enable_audit` | `WithEnableAudit(bool)` | deprecated: audit logging is always on |

`WithStore`, `WithRequireConfig` and `WithVaultOption` round it out. `WithVaultOption` passes a root `vault.Option` through, such as `vault.WithLogger`. Don't use it for `vault.WithConfig`: the extension appends its own `vault.WithConfig`, built from the table above, after your options, so yours is overwritten.

YAML values take precedence over programmatic ones for most fields, and boolean flags set to `true` in code still apply.

## Scope middleware

Vault reads the app, tenant, user and client IP from `context.Context` through the `scope` package. In an HTTP app, put them on the context before your handlers run:

```go
import (
    "net/http"

    "github.com/xraph/vault/scope"
)

// VaultScope puts tenant and user information on the request context
// for Vault operations.
func VaultScope(appID string) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            ctx := scope.WithAppID(r.Context(), appID)

            // Take these from your authenticated session, not from
            // headers the client controls.
            if tenantID := tenantFromSession(r); tenantID != "" {
                ctx = scope.WithTenantID(ctx, tenantID)
            }
            if userID := userFromSession(r); userID != "" {
                ctx = scope.WithUserID(ctx, userID)
            }

            ctx = scope.WithIP(ctx, r.RemoteAddr)

            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}
```

`tenantFromSession` and `userFromSession` stand for your own auth code. Every Vault read and write downstream (secrets, flags, config, audit) picks the scope up from the context.

## Using Vault in handlers

```go
func FeatureFlagHandler(v *vault.Vault) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        // Uses the tenant from the context for overrides and targeting rules.
        enabled := v.Flags().Bool(r.Context(), "new_dashboard", false)
        fmt.Fprintf(w, `{"new_dashboard": %v}`, enabled)
    }
}

func RateLimitHandler(v *vault.Vault) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        // Checks for a tenant override before the app-level value.
        limit := v.Config().Int(r.Context(), "rate_limit", 100)
        fmt.Fprintf(w, `{"rate_limit": %d}`, limit)
    }
}
```

## Secret rotation

The extension starts the rotation manager for you. Register a rotator for each secret you want rotated, for example from a Forge lifecycle hook after registration:

```go
v.Rotation().RegisterRotator("database_url", func(ctx context.Context, current []byte) ([]byte, error) {
    return issueNewDatabaseURL(ctx, current) // your rotation logic
})
```

See [Rotation](/docs/subsystems/rotation) for rotation policies and `RotateNow`.

## Config change watchers

`Watch` runs your callback when a value changes through the config service:

```go
v.Config().Watch("rate_limit", func(ctx context.Context, key string, oldValue, newValue any) {
    // Update your rate limiter, reconfigure a connection pool, etc.
})
```

## Mounting vault into confy

With `mount_to_confy` on, the extension registers Vault as a confy `ConfigSource` and `SecretProvider`, so Vault-managed config and secrets come back through Forge's `ConfigManager`.

```yaml
extensions:
  vault:
    app_id: myapp
    mount_to_confy: true
    confy_key_prefix: "vault."
    confy_mount_keys:
      - db.host
      - api_key
    confy_mount_patterns:
      - "auth.*"
      - "feature.*"
```

Or programmatically:

```go
ext := vaultext.New(
    vaultext.WithAppID("myapp"),
    vaultext.WithMountToConfy(),
    vaultext.WithConfyKeyPrefix("vault."),
)
```

After mounting, Vault config is readable through the config manager:

```go
dbHost := app.Config().GetString("vault.db.host", "localhost")
```

See the [Confy Integration](/docs/guides/confy-integration) guide for details.

## Traces and metrics

You get both without configuring anything. Vault's spans (`get secret`, `set secret`, `rotate secret`, `evaluate flag` and the rest) go to the tracer provider `forge.New` installs, nested under the request that caused them, and the extension passes `app.Metrics()` to the vault so its counters scrape from `/_/metrics` as `forge_vault_*`. The rotation loop and the confy poller start their own root spans, and only when they actually do something.

Grove already times every query the stores make, so you'll see `db.client` spans under Vault's. The [Observability](/docs/subsystems/observability) page lists every span, attribute, metric and label value. None of them carries a secret value, a secret name, a flag key or a tenant.

## Dashboard

The extension registers a `vault` contract contributor with the Forge dashboard, and the React shell reads it through `@forge-go/dashboard-plugin-vault`. Add the plugin to your shell and you get overview, secrets, rotation, flags, config, overrides and audit pages. Nothing needs configuring on the Vault side.

The old templ dashboard is gone, and so is the `github.com/xraph/vault/dashboard` package, so any import of it has to be removed. `MIGRATION.md` in the repo root lists every page and widget the templ version had, and says where each one went or why it didn't.
